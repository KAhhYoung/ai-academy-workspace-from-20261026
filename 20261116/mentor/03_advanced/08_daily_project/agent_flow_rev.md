# LLM 응답 처리 흐름과 A/B 평가

1. 사용자로부터 질문·요청을 API로 입력받는다.
2. FastAPI가 요청을 받아 PostgreSQL의 원본 지식을 조회한다. 그림에는 로그인·권한 정보 조회가 명시되어 있지 않다.
3. 사람이 사용할 자료 ID를 선택하고, 실험에 사용할 지식 정보를 고정 스냅샷으로 남긴다. 이는 원본 DB의 수정을 막는 것이 아니라, 같은 자료로 실험을 비교·재현하기 위한 것이다.
4. 스냅샷을 사용하여 컨텍스트를 구성한다.
5. 다음의 정보를 조합하여 프롬프트를 생성한다.
   - 질문
   - 지식 데이터(컨텍스트)
   - 지시
   - 출력계약
   - 예제
6. 작성한 프롬프트 구성항목을 최소 범위로 수정하여 A,B를 비교 테스트한다.
   1) 같은 질문·문맥·출력 계약 등 비교 조건을 유지하고, 비교하려는 항목만 변경한다.
   2) A/B 평가는 모든 요청이 반드시 거치는 직렬 처리 단계가 아니라, 입력 버전과 실행 결과를 별도로 비교하는 과정이다.
   3) 테스트 결과는 기록으로 남긴다. 응답 원문·검사 결과·근거 검토 기록을 비교하며, 자동으로 승자를 결정하지 않는다.
7. 조립한 프롬프트에 대한 LLM 응답을 받는다. 이번 실습에서는 실제 모델 API 호출을 구현하는 대신 수동으로 받은 응답 또는 테스트용 샘플을 사용하며, 두 출처를 구분하여 기록한다.
8. 출력된 응답에 대해 다음을 자동 검증한다.
   - JSON 문법확인
   - schema 구조확인
   - 참조·상태 규칙 검증
9. 검사 결과에 따라 제한된 재시도 또는 중단을 수행한다.
   1) JSON·스키마 형식 오류에 한해서만 같은 질문·지식·출력 계약을 유지한 채 수정 요청을 추가하여 최대 한 번 다시 응답을 받는다.
   2) 재시도 응답도 다시 검사하며, 두 번째에도 오류가 있거나 형식 오류 이외의 규칙 오류이면 중단한다.
   3) 검사를 통과한 객체 또는 실패를 나타내는 None과 시도별 기록을 반환한다. 유효한 정보 부족 응답은 형식 오류가 아니므로 재시도하지 않는다.
10. 출력 검증 통과 시, 사람의 근거 검토를 거친다.
    1) 질문·답변의 주장·인용 본문을 대조한다. JSON·스키마·참조 규칙을 통과해도 실제 근거가 적합하다는 보장은 없다.
11. 사람의 근거 검토 결과를 FastAPI로 반환하고, API 응답을 통해 사용자에게 결과를 전달한다. 근거가 부적합한 경우에는 검토를 통과한 답변으로 취급하지 않는다.
12. A/B 평가 후 실험 사용자(개발자·운영자)가 사용할 프롬프트 버전을 선택하면, 시스템은 그 선택을 반영하여 이후 요청 처리에 적용한다. 자동 검사와 근거 검토는 품질 확인을 위한 별도 과정이며, 일반 서비스 사용자가 매 요청마다 평가 결과를 확인하거나 프롬프트를 선택하는 것은 아니다.




그림의 범위에 대한 보충:

- FastAPI와 PostgreSQL은 기존 기반이며, 이번 차시의 중심은 고정 스냅샷·컨텍스트·프롬프트·검사·제한된 재시도·평가이다.
- Embedding → 벡터 인덱스 → Retriever를 통한 검색·RAG는 후속 확장으로, 이번 차시에서는 실행하지 않는다. 현재는 사람이 선택한 자료를 사용한다.
- Agent 제어 및 권한 확인 → Tool API 호출도 후속 확장이다. 도구 실행을 도입할 경우 승인된 도구만 실행하고 결과를 LLM에 전달하는 경로가 추가된다.
