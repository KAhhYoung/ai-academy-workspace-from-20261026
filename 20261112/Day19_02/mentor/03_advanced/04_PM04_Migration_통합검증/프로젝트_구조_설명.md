실제 작업 공간에는 `20261102`가 아닌 **`20261112/Day19_02/mentor/03_advanced/04_PM04_Migration_통합검증`** 경로로 존재합니다. 아래는 그 프로젝트의 실제 코드를 기준으로 한 설명입니다. 말씀하신 `test` 폴더의 실제 이름은 `tests`입니다.

이 프로젝트는 **DB 구조를 변경하는 연습**과 **API 요청이 실제 PostgreSQL 데이터에 반영되는지 확인하는 실습**으로 구성되어 있습니다.

```text
04_PM04_Migration_통합검증/
├─ app/                  API 애플리케이션
├─ migration_lab/        DB 구조 변경과 되돌리기 실습
├─ probes/               트랜잭션 동작 확인
├─ recovery/             초기 테이블과 데이터 준비
├─ sql/                  현재 DB 상태 조회
├─ tests/                자동 통합 테스트
├─ requests.http         수동 API 요청 모음
└─ verify_link.py        실행 중인 API와 DB 연결 검증
```

**1. `migration_lab/` — DB 구조 변경 이력을 관리하는 실습**

Migration은 테이블이나 컬럼의 변경을 코드로 기록하고, 순서대로 적용하거나 되돌리는 작업입니다. 이 폴더에서는 **Alembic**을 사용합니다.

| 파일 | 역할 |
|---|---|
| `create_database.sql` | 실습용 DB `day19_migration_h` 생성 |
| `alembic.ini` | Alembic 설정과 Migration 파일 위치 지정 |
| `migrations/env.py` | `MIGRATION_DATABASE_URL` 환경변수로 DB에 연결하고 Migration 실행 |
| `migrations/versions/001_initial.py` | `categories`, `knowledge` 테이블과 제약조건 생성 |
| `migrations/versions/002_source.py` | `knowledge.source` 컬럼과 해당 인덱스 추가 |
| `migrations/script.py.mako` | Revision 파일 템플릿 자리. 현재는 제공된 Revision을 사용한다는 주석만 있음 |

실습 흐름은 다음과 같습니다.

```text
001_initial 적용 → 테이블 생성
002_source 적용  → source 컬럼과 인덱스 추가
001_initial로 되돌리기 → source 컬럼과 인덱스 제거
002_source 재적용 → 다시 추가
```

각 Revision의 `upgrade()`는 변경을 적용하고, `downgrade()`는 변경을 되돌립니다. 주 프로젝트 DB와 분리된 **`day19_migration_h`**에서 진행하도록 구성되어 있습니다.

**2. `probes/` — 트랜잭션의 원자성을 확인하는 실험**

`transaction_probe.py`는 의도적으로 DB 오류를 발생시켜 `rollback()`의 효과를 보여줍니다.

실행 순서는 다음과 같습니다.

1. 임시 카테고리를 추가하고 `flush()`로 INSERT를 DB에 전달합니다.
2. 해당 카테고리를 사용하는 지식 데이터를 추가하되, `content=""`로 설정합니다.
3. 내용 길이 제약조건을 위반하여 `IntegrityError`가 발생합니다.
4. `rollback()`을 실행합니다.
5. 처음 추가했던 카테고리까지 사라졌는지 조회합니다.

정상적인 실험 결과는 다음과 같습니다.

```text
expected IntegrityError
category remained after rollback: False
```

핵심은 **`flush()`가 성공했더라도 `commit()` 전이라면 같은 트랜잭션의 변경을 함께 취소할 수 있다**는 점입니다. 이 스크립트는 앱의 DB 설정을 사용합니다.

**3. `recovery/` — 초기 DB 준비가 누락된 경우 사용하는 SQL**

`prepare_if_missing.sql`은 다음을 생성합니다.

- `categories`, `knowledge` 테이블
- 기본키, 외래키, 고유값, 문자열 길이 제약조건
- `learning`, `environment`, `reference` 카테고리
- 예제 지식 데이터 3건

이름은 `recovery`이지만, 내용상 **백업 복원 도구보다는 초기 실습 환경 준비용 스크립트**입니다.

`CREATE TABLE IF NOT EXISTS`를 사용하지 않으므로, 기존 테이블이 있는 상태에서 반복 실행하는 용도는 아닙니다.

**4. `sql/` — 현재 DB 상태를 확인하는 조회문**

`check_pm_start.sql`에는 실습 시작 전 상태를 확인하는 `SELECT` 문이 있습니다.

| 조회 내용 | 확인 목적 |
|---|---|
| `current_database()`, `current_user` | 현재 접속한 DB와 사용자 확인 |
| 카테고리 개수 | 기본 데이터 준비 여부 확인 |
| 지식 데이터 개수 | 실습 시작 시 데이터 수 기록 |
| `knowledge`와 `categories` JOIN | 지식 데이터와 카테고리 이름을 함께 확인 |

데이터를 변경하지 않고, **실습 전 기준 상태를 기록하는 역할**입니다.

**5. `tests/` — API와 실제 PostgreSQL을 자동 검증**

별도 테스트 DB인 **`day19_test_h`**를 사용합니다.

| 파일 | 역할 |
|---|---|
| `create_database.sql` | 테스트 DB 생성 |
| `prepare_test_schema.sql` | 테스트용 테이블과 기본 데이터 준비 |
| `test_integration.py` | API 생성·삭제 결과를 DB 조회로 자동 검증 |
| `README.md` | 테스트 환경 설정과 실행 방법 안내 |

`test_integration.py`는 다음을 검사합니다.

```text
API POST 요청
  → HTTP 201 확인
  → 응답 id로 DB 조회
  → 저장된 title 확인
API DELETE 요청
  → HTTP 204 확인
  → DB에서 해당 id의 행 개수가 0인지 확인
```

FastAPI의 `get_db` 의존성을 테스트용 Session으로 교체하므로, 요청 처리는 테스트 DB를 사용합니다.

또한 `TestClient`로 앱을 호출하므로 **별도 Uvicorn 서버는 필요하지 않지만, 실제 PostgreSQL은 필요**합니다. `TEST_DATABASE_URL`이 없으면 테스트를 건너뜁니다.

**6. `requests.http` — API를 직접 호출하는 요청 모음**

다음 요청들이 작성되어 있습니다.

- 서버 상태 확인: `GET /health`
- 지식 목록 조회: `GET /api/knowledge`
- 카테고리 필터 조회
- 지식 생성: `POST`
- 지식 수정: `PUT`
- 지식 삭제: `DELETE`

VS Code의 REST Client 같은 도구에서 요청을 하나씩 실행하며 응답을 확인하는 용도입니다.

수정·삭제 예시에 적힌 ID `4`는 고정된 정답이 아닙니다. **생성 응답에서 받은 실제 ID로 바꿔야 합니다.** 이 파일 자체에는 결과를 자동 판정하는 검증 코드가 없습니다.

**7. `verify_link.py` — 실행 중인 API와 DB를 같은 ID로 대조**

이 스크립트는 서버에 실제 HTTP 요청을 보내고, DB에도 직접 접속합니다.

```text
POST로 임시 데이터 생성
  → 응답에서 id 획득
  → 같은 id를 DB에서 직접 조회하고 출력
DELETE로 해당 데이터 삭제
  → 삭제 응답 상태 출력
  → DB에 남은 행 개수 출력
```

정상적으로 진행되면 생성된 DB 행이 출력되고, 삭제 상태는 `204`, 삭제 후 `DB remaining`은 `0`이 됩니다.

기본 API 주소는 `http://127.0.0.1:8000`이며 `API_BASE` 환경변수로 변경할 수 있습니다. DB 접속 정보는 앱 설정을 사용합니다.

`tests`와 목적은 비슷하지만 차이가 있습니다.

| 구분 | `tests/test_integration.py` | `verify_link.py` |
|---|---|---|
| API 호출 | `TestClient`로 앱 내부 호출 | 실행 중인 서버에 HTTP 요청 |
| DB | 별도 테스트 DB | 앱 설정에 지정된 DB |
| 결과 확인 | `assert`로 자동 판정 | 출력된 값을 확인 |
| 주요 목적 | 코드의 통합 동작 검사 | 실제 서버와 DB 연결 확인 |

전체적으로 **`migration_lab`은 DB 구조 변경**, **`probes`는 트랜잭션**, **`recovery`는 초기 준비**, **`sql`은 상태 조회**, **`requests.http`는 수동 호출**, **`tests`와 `verify_link.py`는 API·DB 통합 검증**을 담당합니다.
